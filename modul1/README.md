## Быстрый запуск

```bash
cd project2-deadlocks
chmod +x run_all.sh
./run_all.sh
```

Скрипт проверяет синтаксис и запускает все программы, которые завершаются самостоятельно. Полная проверка философов занимает около 30 секунд: по 10 секунд на каждый вариант.

```bash
python3 -m unittest -v test_project.py
```

Исходную взаимоблокировку запускайте отдельно:

```bash
python3 transfer_deadlock.py 2>&1 | tee outputs/transfer_deadlock.txt
```

Через 5 секунд `faulthandler` печатает стеки потоков и завершает процесс. Это намеренное поведение.

## Блок A. Базовый

### A1. Диагностика исходной взаимоблокировки

В `transfer_deadlock.py` два кассира переводят деньги в противоположных направлениях:

- `кассир-1` захватывает блокировку счёта A и ждёт блокировку B;
- `кассир-2` захватывает блокировку счёта B и ждёт блокировку A.

По стеку `faulthandler` оба потока находятся на строке:

```python
with locks[dst]:
```

Первый поток ждёт `locks["B"]`, второй ждёт `locks["A"]`. Получается цикл:

```text
кассир-1 -> счёт B -> кассир-2 -> счёт A -> кассир-1
```

### A2. Исправление без sleep и timeout

В `transfer_fixed.py` оба потока берут блокировки в одном глобальном порядке: сначала A, затем B. Направление денежного перевода при этом может быть любым.

```python
first, second = sorted((src, dst))
with locks[first]:
    with locks[second]:
        ...
```

Такой порядок нарушает четвёртое условие Коффмана: **циклическое ожидание**. Цикл построить невозможно, поэтому взаимоблокировка исключена. `sleep` и `timeout` для исправления не используются.

Проверяется также инвариант денег:

```text
A + B = 2000
```

### A3. Алгоритм банкира

Для каждого процесса рассчитывается остаточная потребность:

```text
Need = Max - Allocation
```

Процесс можно условно завершить, если:

```text
Need[i] <= Work
```

После условного завершения он возвращает выделенные ресурсы:

```text
Work = Work + Allocation[i]
```

Результаты:

| Файл | Результат | Последовательность |
|---|---|---|
| `bank_state.txt` | SAFE | P4, P3, P1, P2, P0 |
| `bank_state2.txt` | UNSAFE | завершается только P4; P0, P1, P2, P3 остаются |

Команда:

```bash
python3 banker.py data/bank_state.txt data/bank_state2.txt
```

## Блок B. Основной

### B1. Проверка запросов

Каждый запрос из `requests.txt` проверяется независимо относительно исходного `bank_state.txt`. Изменения одного запроса не переходят к следующему.

| Запрос | Решение | Причина |
|---|---|---|
| `P2 1 0 0` | GRANT | состояние остаётся безопасным |
| `P0 0 1 0` | REFUSE | после выдачи состояние небезопасно |
| `P3 0 1 0` | GRANT | состояние остаётся безопасным |
| `P4 2 0 0` | ERROR | запрос превышает объявленный `Need=[1,0,1]` |
| `P1 1 0 1` | REFUSE | после выдачи состояние небезопасно |

Команда:

```bash
python3 banker.py data/bank_state.txt --requests data/requests.txt
```

Алгоритм сначала проверяет `Request <= Need`, затем `Request <= Available`, временно выдаёт ресурсы и запускает проверку безопасности. При небезопасном результате временные изменения отбрасываются.

### B2. Граф ожидания

`wait_graph.py` последовательно проигрывает события `acquire`, `wait` и `release`, определяет владельца каждого ресурса и строит рёбра:

```text
ожидающий процесс -> процесс-владелец
```

На конец журнала:

```text
P3 -> P4
P4 -> P5
P5 -> P3
P6 -> P2
P7 -> P5
```

Алгоритм Тарьяна находит компоненты сильной связности. Цикл состоит из `P3`, `P4`, `P5`.

### B3. Участники и зависимые процессы

- `P3`, `P4`, `P5` непосредственно входят в цикл.
- `P7` не входит в цикл, но ждёт `P5`, поэтому также не сможет продолжить.
- `P6` ждёт `P2`, который сам не заблокирован. По имеющемуся журналу это ожидание не является частью deadlock.

Команда:

```bash
python3 wait_graph.py data/waitlog.txt
```

## Блок C. Продвинутый

### C1. TrackedLock

`TrackedLock` оборачивает `threading.Lock` и хранит:

- имя блокировки;
- текущего владельца;
- рёбра ожидания между потоками.

Если поток не может сразу захватить блокировку, добавляется ребро `ожидающий -> владелец`. После каждого добавления выполняется поиск цикла. При обнаружении цикла выбрасывается `DeadlockDetected`, а контекстный менеджер освобождает уже захваченные блокировки.

```bash
python3 transfer_tracked.py
```

Результат: цикл обнаруживается до вечного зависания, оба потока завершаются, сумма денег остаётся равной 2000.

### C2. Обедающие философы

```bash
python3 philosophers.py --duration 10
```

Программа запускает три варианта по 10 секунд каждый.

1. **Наивный вариант.** Все пять философов одновременно берут левую вилку, затем ждут правую. Все пять потоков оказываются во взаимоблокировке.
2. **Упорядоченный захват.** Каждый философ сначала берёт вилку с меньшим номером. Циклическое ожидание невозможно.
3. **Официант.** Семафор допускает к вилкам не более четырёх философов. Хотя бы один философ всегда остаётся без первой вилки, поэтому кто-то может собрать пару и освободить ресурсы.

Для каждого философа выводятся:

- сколько раз он поел;
- максимальное время ожидания;
- остались ли зависшие потоки.

Числа могут немного отличаться между запусками из-за планирования потоков, но итог должен быть стабильным: наивный вариант зависает, два исправленных варианта завершаются без зависших потоков.

## Четыре условия взаимоблокировки

Deadlock возможен, только если одновременно выполняются все условия Коффмана:

1. **Взаимное исключение:** ресурсом одновременно пользуется один поток.
2. **Удержание и ожидание:** поток держит один ресурс и ждёт другой.
3. **Отсутствие принудительного изъятия:** ресурс освобождает только владелец.
4. **Циклическое ожидание:** существует замкнутая цепочка ожидающих потоков.

Исправление переводов и упорядоченный вариант философов устраняют циклическое ожидание. Вариант с официантом не позволяет всем пяти философам одновременно удерживать по одной вилке.

## Ответы на возможные вопросы

**Почему sleep не исправляет deadlock?** Он только меняет вероятность и момент возникновения. Все четыре условия взаимоблокировки сохраняются.

**Чем небезопасное состояние отличается от deadlock?** При deadlock процессы уже не могут продолжить. Небезопасное состояние означает, что система не может гарантировать завершение при будущих запросах, хотя процессы ещё могут работать.

**Почему запрос P4 является ошибкой, а не отказом безопасности?** Он превышает заранее объявленный максимум процесса, поэтому нарушает входные условия алгоритма банкира ещё до проверки безопасности.

**Почему P7 заблокирован навсегда, хотя не входит в цикл?** P7 ждёт ресурс P5. P5 находится внутри цикла и никогда не освободит ресурс без внешнего вмешательства.

**Почему у исправленных философов статистика отличается?** Планировщик ОС выбирает порядок запуска потоков недетерминированно. Важны отсутствие зависания и возможность каждого философа поесть.
